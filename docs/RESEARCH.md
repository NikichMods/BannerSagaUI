# Инженерные данные — 19 октября 2026

## Needle: пригодность штатного источника прямых изменений —21.10.2026

Вопрос после согласования ограниченной семантики: можно ли использовать `BattleAbility.getStatChange(STRENGTH)` отдельно для каждой фигуры штатной линии и получить фактические прямые потери ARM/STR без расчёта ответных каскадов? **Статический ответ: пара чисел существует и полезна, но bare-вызов не удовлетворяет принятому требованию во всех состояниях TBS1.** Не требуется возвращаться к полному «оракулу»; обнаруженные исключения относятся к самому попаданию и безопасному вызову.

Метод: повторно использованы существующие AS-экспорты, точный оригинал TBS1 2.58.17 / build3268685 SHA-256 `7d24a5910b9a0b3dfdae21443e3f0b7edd2510d6269d8407b6d0d31a5178a317`, FFDec26.4.0 p-code восьми методов из пяти классов, отдельный AS-export StatType, read-only AMF3-разбор52определений `saga1/items1.json.z` и уже прочитанных способностей. Новый симулятор/игровая проба не создавались; методы не исполнялись. Локальный evidence manifest и хеши exports/сохранений — local/RESUME.md. Числовые контрпримеры ниже — выводы из веток кода, не runtime-наблюдения.

| Свойство | Владелец / установленное поведение | Следствие для Needle |
| --- | --- | --- |
| Две величины | getStatChange читает до/после Stats цели; при STRENGTH возвращает STR-разницу в amount, ARM-разницу в other и missChance | Popup теряет other, но источник его уже считает; базовую формулу урона переписывать не требуется |

| Прочие защиты | В fake пропускаются armor/willpower absorption, DAMAGE_ABSORPTION_SHIELD, damage recourse, talent/диверсия и некоторые другие ветви | Нельзя молча считать их учтёнными. Важное уточнение исследования: первоначальная промежуточная формулировка «штатные числа уже ограничены остатком характеристики» верна для брони, но не для силы. Проверка StatType установила различие. Штатная величина удара и принятая для UI фактическая потеря доступного ресурса — разные семантики; не менять исходный Stat/урон ради показа меньшего числа.

### Условия названий реакций

`StatChangeData` не передаёт tags/annotations/effects временного попадания, поэтому amount/other не дают готового надёжного списка реакций. В Op_WaitForActionComplete проверены checkWatchStats и abilityCompleteHandler: учитываются caster/target POV, tags, annotated delta, parent/root ограничения, ownerMustBeAlive/effectMustBeIntact, допустимость response targets и их дистанция. Например, Splinter смотрит на annotated ARM delta≤−3, Return the Favor имеет собственный ответный MELEE range1; одного наличия пассивы недостаточно. `checkTargetValidity` проверяет только часть этих условий и не является полным predicate срабатывания.

Сам handler для запроса использовать нельзя: он изменяет operants, blockComplete и создаёт дочерние действия. Для предпросмотра достаточно проверять только условия конкретно обозначаемой реакции; исполнять ответ или строить общий движок всех триггеров не нужно. Расчёт её урона по принятой границе исключён. Если данные о непосредственном попадании не позволяют гарантировать условие, название нельзя выдавать как гарантированное срабатывание.

### Выбор ближайшего технического пути

1. **Отклонён bare-loop getStatChange как готовый общий provider:** есть реальные TBS1 исключения для непосредственного попадания, неявные ошибки и известный fake-cache boundary. Не устранять это включением live-исполнения или глобальной правкой getStatChange/fake guards.
2. **Предпочтительный исследовательский путь — ограниченный адаптер штатного прямого расчёта:** сохранить native DAMAGE_STR/CHANGE_STAT, нормализовать представление потери, явно проверять условия, где fake расходится с обычным исполнением; использовать уже изученную изоляцию fresh fake Stats/обязательный cleanup. Числа и доказанные reaction annotations должны передаваться прямо, а не извлекаться из журнала. Проверить, достаточно ли оболочки getStatChange или выгоднее узкий Effect/Op seam, уже исследованный для Ram; это ещё не выбранная production реализация.
3. **Не обоснованы** переписывание формулы урона, полный fake-мир и расчёт исключённых ответных каскадов. Исследовательские guards не являются согласованным ограничением будущего релизного охвата; пользовательский fallback и stochastic UI остаются открытыми.

**Production gate: BLOCKED для нового provider.** Наблюдаемое свойство/owner/final writer установлены: фактические прямые ARM/STR-потери Needle, DAMAGE_STR/CHANGE_STAT→Stats, отдельные условия реакций. Предполагаемый blast radius — новый локальный provider/передача результата, без замены глобальных host helpers; сохраняются targetSet/commit, live Stats/modifiers/effects/RNG, бой/saves, Ram/test.10. Ещё не доказаны безопасный новый boundary и handling выявленных immediate conditions; READY не объявлен. Минимальное принятие механизма потребует реальной сверки пары чисел до/после на доступной линии и восстановления; статические exports/компиляция её не заменяют.

## FPS карточки героя: проба остановки портрета — 20.10.2026

Пользователь сообщил о воспроизводимом падении примерно 100→20 FPS в открытой карточке разных героев с восстановлением после выхода; без геймпада эффект тот же. Показатель CPU в NVIDIA overlay растёт примерно 20→50%, но это не профиль функций и не доказанная загрузка только процесса игры. Windows 7 compatibility не помогла; `starling=false` снизил FPS и в остальной игре. Обе настройки сняты. Точное совпадение симптомов есть в [прямом сообщении игрока TBS1](https://steamcommunity.com/app/237990/discussions/0/1762482479183748057/); причинная связь с AIR там также не доказана.

**READY только для диагностической пробы:** TBS1 2.58.17 / build 3268685. В `GuiPgDetails.update(int)` при видимой карточке вызывается `portrait.update(delta)` для живого выбранного героя. `GuiIcon.update` продвигает `anim.clip` и вызывает `anim.update`; тип — `XAnimClipSpriteFlash`. В той же функции отдельно обновляются promotion, stats и gp. Проверен экспорт из фактического DEV SWF; прежний AS-export GuiPgDetails имеет SHA-256 `47c1bb98e47e3f9fb3c940cec7191d37b61a1a983b33e8a892fbdb96eeea8d02`. Это кандидат на измерение, не установленная причина.

Проба test.7 убирает только вычисление аргументов и вызов `portrait.update` в этом методе, заменяя инструкционный диапазон равным числом NOP. Длины, адреса переходов, сигнатуры, константы и остальные тела сохраняются; другие потребители `GuiIcon` не меняются. Инициализация/загрузка изображения и остальные обновления карточки остаются штатными. Поведение непостоянное, не записывается в сохранение; откат — прежний DEV SWF и его манифест. Возможность увидеть неподвижный портрет, отсутствие другого пути его анимации и эффект на FPS требуют runtime-проверки. Если портрет не появился или продолжает двигаться, отрицательный результат FPS не опровергает гипотезу корректно.

`tools/research/build_portrait_freeze.py` использует неизменяемый test.6 как доказанный производный вход исходной базы, дополнительно сверяет тело update с проверенным оригиналом. Новый файл — отдельный test.7; test.6 не пересобирается и не переименовывается. Для DEV SteamEntry-адаптация применяется отдельно; точная установка и исходы принадлежат TEST_BUILD_LOG.md. Следующий тест: та же карточка без действий, наличие статичного портрета, FPS/CPU, затем выход и проверка прежней плавности. Производственное отключение анимации не принято.

**Runtime-свидетельство test.7:** пользователь сообщил восстановление примерно 100 FPS вместо 20; установленный хеш и штатный Starling подтверждены свежим журналом. Узкая разница между DEV test.6 и test.7 локализует эффект к пропущенному обновлению портрета в этом сеансе. Стоимость `clip.advance`, `anim.update` и дальнейшей отрисовки по отдельности пока не измерена; видимость/неподвижность портрета и CPU после пробы отдельно не подтверждены. Это основание исследовать анимационный путь, а не менять AIR/настройки Windows наугад. Точный сеанс и ограничения сохранений — TEST_BUILD_LOG.md.

**Standalone test.8:** пользователь отдельно разрешил установку FPS-исправления в личную Steam-игру. `--standalone` применяет тот же десятибайтовый NOP-диапазон только к проверенному оригинальному SWF; пробы Тарана, локализации и DEV SteamEntry не включаются. READY переиспользует доказанный метод/область действия test.7, с дополнительной проверкой, что от оригинала отличается только тело 18301. Это личная установка обхода проблемы, не согласие на Nexus-публикацию или stable-релиз. DEV test.7 сохраняется. Перед заменой требуются закрытая целевая игра, проверенный оригинальный хеш и backup; установка и Steam-runtime имеют отдельный статус.

**Решение 21.10.2026:** пользователь подтвердил отсутствие просадки в основной Steam-игре и принял статичный портрет как приемлемый компромисс первого самостоятельного FPS-мода: потеря малозаметной анимации существенно менее важна, чем падение FPS. Steam-session и payload сверены, подробности — TEST_BUILD_LOG.md. Сохранение движения/поиск дорогой внутренней операции больше не является обязательным условием первого выпуска; возвращаться к оптимизации при отдельной потребности. Первый заявляемый охват — карточка героя TBS1 Steam Windows на проверенной базе, без обещания общего ускорения игры. После отдельного запроса создан BannerSagaFPSFix: его Windows-патчер и откат проверены на изолированной копии, результат совпал с test.8. Последующими кандидатами/приёмкой установщика владеет новый проект; Nexus-публикация ещё не выполнена.

## «Таран»: источник итогов и временная цель, 20.10.2026

**Вопрос:** можно ли получить полные конечные броню/силу для полевого предпросмотра, используя штатный расчёт, и показывать их от hover/focus без изменения выбранной команды и применения? Исследованы классы именно установленного TBS1 SWF; его SHA-256 повторно совпал с data/baseline.json. Это статическое исследование, без запуска/патча игры и без нового свидетельства после применения.

### Что действительно даёт штатный прогноз

BattleAbility.getStatChange валидирует одну способность и одну цель, временно включает BattleBoard.fake, исполняет тестовую способность и возвращает разность характеристики цели. При запросе STRENGTH дополнительно возвращается разность ARMOR. StatChangeData содержит amount, other и missChance; это не снимок конечных характеристик всех участников. При исходном значении запрошенной характеристики 0 функция не запускает расчёт и возвращает false. Это особенно важно для будущего показа нулевой брони: отсутствие такого расчёта не означает отсутствие результата.

BattleBoard.fake переключает abilityManager и fake-статистики всех сущностей. Entity.setFakeEntityStats клонирует/синхронизирует Stats; Entity.stats выбирает настоящие или fake-статистики. Это **не копия всей сцены, позиций, постоянных эффектов и жизненного цикла**. Стоимость в BattleAbility.deductCosts в fake-режиме не списывается: расход нельзя получить как изменение воли такого прогноза, его владелец — costs выбранного определения способности.

Для «Тарана» есть два независимых запрета: его эффект помечен NO_FAKING, и Effect.execute в fake-режиме возвращает FAIL до создания операций; кроме того, Op_BatteringRam.apply сам прекращает работу при fake/faking. Поэтому простое включение displayDamageUI или вызов getStatChange для abl_batteringram **не даёт итог «Тарана»**. При успешной валидации getStatChange может вернуть true и нулевую разность: true не означает полноту прогноза. Запрет NO_FAKING не снимать ради предпросмотра.

### Где возникает настоящий результат

В реальном Op_BatteringRam.apply сначала исполняется штатная подспособность abl_batteringram_initial_arm_dam текущего ранга. Затем, если разрешено отбрасывание, создаётся принудительный BattleMove. Дополнительные abl_batteringram_fallthrough_arm_dam исполняются по событиям INTERSECT_ENTITY уже во время перемещения. Каждая живая, не GHOSTED пересечённая сущность учитывается один раз, даже если занимает несколько клеток; она становится caster подспособности, а целью остаётся отбрасываемый воин. Нельзя заменить это уроном пересечённому воину или одним бонусом на каждую занятую им клетку. NO_KNOCKBACK останавливает именно перемещение после начального эффекта.

Конечная клетка вычисляется Op_KnockbackHelper.getKnockbackStopTile. Тем же владельцем пользуется AbilityDestinationOverlay для штатных стрелок. Но сам overlay берёт первую **уже выбранную** цель из turn.ability.targetSet и обновляется от TURN_ABILITY/TURN_ABILITY_TARGETS/TURN_COMMITTED; hover он самостоятельно не потребляет. Конечная клетка и список состоявшихся пересечений — разные данные: одна конечная точка не доказывает весь урон.

Подспособности используют Op_ChangeStat. Итог не сводится к вычитанию поля amount: execute/apply учитывают ограничения, сопротивление, текущую базу и нижнюю границу брони 0; apply повторно вычисляет значение и записывает Stat.base. В общем коде есть также ветви перенаправления/ответных эффектов. Их фактическое наличие у показанных бойцов из скриншота не установлено. Полный настоящий результат заканчивается после перемещения и связанных эффектов, а не после первого изменения брони.

Даже использование штатных подспособностей в fake-режиме пока не доказывает полный результат: Op.handleDivertArmor пропускает вероятностное отклонение; processResistance пропускает генерацию талантов после детерминированного сопротивления; Op_ChangeStat не выполняет damage recourse в fake. Это свойства общего клиента, не доказательство наличия всех этих механик в доступном сценарии TBS1. AbilityManager продолжает отправлять события выполнения/завершения в fake-режиме. Следовательно, fake нельзя объявить универсальной изолированной транзакцией только по копированию Stats.

### Уточнение числового прогноза: движение, ауры и нижний seam, 20.10.2026

После подтверждения штатного перебора целей геймпадом продолжено статическое исследование конечных чисел, без изменения игры. Вход — оригинальный SWF `7d24a5910b9a0b3dfdae21443e3f0b7edd2510d6269d8407b6d0d31a5178a317`, FFDec 26.4.0. Дополнительные экспорты и их хеши сохранены локально; manifest SHA-256 `79d1f5dc72ada7612d8dc15d265e0513f9634a09c519c6f3b0f26ce5e06d77f3`. Это статические факты TBS1, не runtime-подтверждение прогноза или совместимости продолжений.

**Обычный для TBS1 контрпример узкому подсчёту урона — «Стена щитов».** pas_shieldwall использует Op_Aura; abl_shieldwall_bonus и abl_shieldwall_bonus_self добавляют модификатор ARMOR через Op_IntStatMod, не меняют базовую броню. Op_Aura слушает MOVE_FINISHING и пересчитывает отношения соседства. BattleEntityMobility.walkTilesCompleteHandler отправляет MOVE_FINISHING до move.setExecuted, поэтому снимок после последнего подэффекта урона ещё не доказывает окончательные видимые числа. Сдвиг носителя ауры/её получателя может изменить броню соседей, которым прямой урон не наносился. Какие именно связи меняются в конкретном кадре пользователя, пока не установлено.

Практическое следствие: показывать нужно Stat.value / Stats.getValue, а не только Stat.base; учитывать изменившиеся ауры у затронутых соседей. Нельзя ради пробы переместить настоящую фигуру и запустить её Op_Aura: checkOther/auraAdd/auraRemove меняют словари дочерних способностей и постоянные эффекты. Stat.clone копирует StatMod с прежним provider; клонированные числа не означают клонированные владельцы эффектов. Безопасную проекцию соседства требуется доказать отдельно, без событий настоящего движения.

Точное статическое правило pas_shieldwall: для каждого соседнего живого/включённого союзника владелец получает отдельный self-модификатор ARMOR +1, а союзник — отдельный aura-модификатор ARMOR +1; соседу не обязательно иметь эту пассивку. Определение бонуса использует FRIENDLY_OTHER, rangeMax=1; TileRectRange.computeRange складывает разрывы по двум координатам между занимаемыми прямоугольниками. Для неперекрывающихся фигур это соседство общей стороной, не углом; крупная фигура учитывается как один союзник, не по числу клеток соприкосновения. Модификаторы STACK: по изученному коду пара соседей, каждый со своей pas_shieldwall, получает по два бонуса на фигуру — от своей и чужой пассивки. Это вывод из данных/Op_Aura, отдельно в runtime не испытан. Разрыв связи убирает соответствующие self/other-модификаторы, создание добавляет их; отсюда достаточная локальная область проверки ауры при одиночном сдвиге без иных событий — исходные и конечные связи переносимой фигуры. Это уточняет ограниченную геометрическую задачу, но не снимает отдельно установленные вопросы реального урона, ответов и опасностей.

**Пересечения и поле:** WalkTilesBehavior._checkMovementResults собирает всю площадь фигуры через _collectIntersectChecks, затем посылает INTERSECT_ENTITY; обработчик «Тарана» заново просматривает residents текущего rect и исключает уже учтённые/мёртвые/GHOSTED сущности. Это не один бонус на клетку. Фактическое срабатывание ответа в конкретном «Таране» зависит от владельца, враждебности и момента/дальности; здесь оно не заявлено.

До выбора цели новый путь разрешён только для SPECIAL_BATTERING_RAM: мышиный ввод, управляемый игроком caster, отсутствие tutorial restrictInput и незавершённого плана движения длиннее одной позиции. ## Рабочая копия без Steam и изоляция данных

Цель пользователя: Steam учитывает только личную игру; рабочие сеансы не увеличивают счётчик. Быстрый вход в бой желателен лишь при малой дополнительной сложности. Это инфраструктура разработки, не новая функция распространяемого мода.

Проверено на исходном TBS1 2.58.17 (SWF baseline из data/baseline.json), выборочным FFDec-экспортом GameMainDesktop, SteamEntryHelper, GameEntryDesktop, AppInfo, AirAppInfo, GenericEntryHelper и GameOptions. Сырые классы остаются в игнорируемом local/dev-launch-inspection. SteamEntryHelper задаёт allowUserBypass из AppInfo.isDebugger; processArgument принимает значение steam только при allowUserBypass. В сохранённом реальном журнале test.2 isDebugger=false. Поэтому steam=false в обычном установленном AIR не отключает интеграцию. developer/dev отдельно включает инструменты разработки и этот guard не меняет.

При обычном setup выполняются SteamAPI_Init и SteamAPI_RestartAppIfNecessary. Прямой ярлык EXE сам по себе не доказывает независимость от Steam. При enableSteam=false Steamworks не создаётся, выбирается GenericEntryHelper.performGenericPlatformSetup; достижения/лидерборды/DLC-проверка становятся null-реализациями, облачные сохранения Steam не выбираются. Это не доказывает изоляцию локальных сохранений: отдельный каталог игры сам по себе её не обеспечивает.

GameEntryDesktop штатно разбирает happening/book/bk, saga_start и load (включая профиль после двоеточия). Существование аргументов не доказывает готовый автономный сценарий боя с корректным отрядом и без побочных записей. Такой сценарий не проверен.

**Реализовано и принято 20.10.2026:** отдельная локальная DEV-копия стала средой дальнейшей разработки. Закрывать Steam больше не требуется в проверенной конфигурации; первоначальная блокировка снята после контрольного сеанса. Порядок работы — DEVELOPMENT_ENVIRONMENT.md, точные испытания — TEST_BUILD_LOG.md. Offline mode, скрытие статуса и последующее уменьшение времени не используются.

### Узкое разрешение штатного режима

База адаптации — неизменяемый SWF test.2 SHA-256 `ccb2918b8dd04d47e83261a4b210146904f85b13adebd6fb4110b3c4bc3597fa`, уже содержащий Ram hover. В SteamEntryHelper.processArgument снята только debugger-проверка в ветви `steam`; проверка `steam_id` сохранена. Узкий импорт полного p-code метода: DoABC tag 3671, method_info 612, body_index 599; код 125 → 122 байта. Независимое структурное сравнение показало одно изменённое тело, прежние frame/header, таблицы, константы, сигнатуры, метаданные метода и все остальные тела. Повторный AS-экспорт подтверждает изменение нужной ветви. Сырые p-code/экспорты остаются локальными.

Установленный составной DEV-SWF SHA-256 `b01dd6538606bfb69e0f2b41b82b8d69766f7cc5b27f039aaa962a13555c359c`. Он не является побайтово прежним номерным test.2: исходный кандидат и его манифест не заменены. При явном `steam=false` запускается прежний GenericEntryHelper.performGenericPlatformSetup, SteamAPI_Init/RestartAppIfNecessary не достигаются. Это настройка частной среды, не принятый состав распространяемого мода; при новой базе нужно заново проверить seam, не переносить старое тело вслепую.

### Независимое хранилище и ловушка INI

В дескрипторе копии изменён AIR application ID с TheBannerSaga на TheBannerSagaDev и заголовок окна. AirAppInfo/SaveManagerAir работают через File.applicationStorageDirectory; журнал реального запуска подтвердил новый каталог. Сохранения и настройки скопированы один раз без правки содержимого. Для всех 12 пар проверены разные физические файлы, отсутствие symlink/junction в проверенных деревьях и неизменные SHA-256 оригиналов. Это сильнее, чем разные текстовые пути. Бой/новое автосохранение в DEV этим меню-сеансом не проверены.

INI хранить с переносами **LF**. AppInfo.parseIni убирает только первый CR, затем делит по LF и сохраняет значения без trim. Перезапись исходного LF-файла в CRLF оставила CR в sku, locale и пути saga; первый запуск завершился после ошибок загрузки локали/кампании. Исправлено восстановлением исходных значений с LF и добавлением args; следующий запуск загрузил меню и штатно завершился. Не исправлять это патчем общего парсера. Дескриптор XML/скрипт PowerShell не имеют этого ограничения.

Основной локальный запускатель проверяет хеши важных файлов по dev-support/dev-manifest.json, ID/дерево хранилища и отсутствие второго экземпляра игры. Аргументы — steam=false locale=ru; developer-режим не включён. После проверки совместного сеанса условие запрета открытого Steam удалено; остальные проверки сохранены. Прямой запуск без проверенных аргументов и запуск из Steam-библиотеки этой проверкой не охвачены.

Техническая основа AIR storage: [AIR SDK, File objects](https://airsdk.dev/docs/development/files-and-data/working-with-the-file-system/using-the-air-file-system-api/working-with-file-objects-in-air). Возможность возврата прямого EXE-запуска в Steam при штатной интеграции согласуется с [Steamworks API Overview](https://partner.steamgames.com/doc/sdk/api?l=english). Вывод о конкретной DEV-копии основан на её коде, хешах и локальном runtime-свидетельстве, а не на общем обещании документации.

### Отказ компиляции диагностической ветки: стек finally, 20.10.2026

Test.3 не дошёл до вычисления: VerifyError #1030 при старте тренировочного боя, точный журнал/откат — TEST_BUILD_LOG.md. По [таблице ошибок Adobe](https://github.com/adobe/avmplus/blob/master/core/ErrorConstants.h) #1030 — kStackDepthUnbalancedError; [Verifier::mergeState](https://github.com/adobe/avmplus/blob/master/core/Verifier.cpp) отклоняет объединение путей с разной высотой operand stack. Сам кадр onAbilityFinalComplete в журнале не локализует отказ внутри его собственного тела.

Оригинальный ограниченный анализатор check_pcode_stack.py обнаружил в замороженном доноре и трансплантированном getStatChange пути с высотами 0/1 и underflow у lookupswitch внешнего finally. Обычный путь несёт служебный номер продолжения finally на стеке; вход в catch очистки очищает стек до одного исключения, после его потребления служебного значения больше нет. То есть дефект уже в компиляции донорского AS, а не только в переносе activation slots. Удаление только внутреннего finally сохраняет дефект; контрольное упрощение до общего участка после catch-all устраняет его. Это объяснение статически найденного дефекта, согласованного с runtime-ошибкой; принятие исправления AIR ещё требует запуска.

В новой пробе расчёт ловит все значения исключений; catch сохраняет данные без форматирования. Обе ветки доходят до очистки, её catch также только сохраняет данные; затем снимается board.fake, проверяются реальные инварианты и формируется сообщение. Неномерная полная проверочная сборка дала SHA-256 `030b5d0e594a0d25c087064af362deba5191185a4ec903eb2ec47dc8a59cbcb5`, все шесть повторно экспортированных изменённых методов проходят проверку высот; прежние проверки изоляции и штатной ветки тоже проходят. Бинарник не устанавливался; он не заменяет test.3 и не является номерным кандидатом.

Сборщик теперь проверяет донор, расчёт после переноса и повторный экспорт всех шести методов; неизвестная инструкция останавливает проверку. Анализатор не проверяет типы, QName/доступ, достоверность границ исключений или игровую корректность. Пять синтетических тестов проверяют потерю служебного значения на catch-пути, общий cleanup, конфликт высот, underflow/лимит и неизвестный opcode. Следующий номер test.4 должен сначала пройти вход в бой; только затем проверяется прежняя числовая гипотеза. Механизм полного fake-мира не выбран: выявлен локальный дефект компиляции, а не новое доказательство необходимости широкого симулятора. Производственный прогноз остаётся BLOCKED.

### Оценка инженерного фундамента перед расширением прогноза, 20.10.2026

Пользователь уточнил приоритет: накапливать проверяемое понимание и строить надёжный мод с минимальным вмешательством, а не просто получать очередной работающий результат. Текущий итог разделяется на три области. База установки/точной идентичности/отката и ограниченный hover test.2 имеют прямые свидетельства. Числовая проба test.4 использует родные операции, но её безопасный жизненный цикл и полнота ещё не доказаны. Сборка собственного AS через экспериментальный компилятор FFDec и перенос activation slots остаются отдельной хрупкой границей, которую проверка высот стека лишь частично контролирует.

Временные приёмы пробы — диагностический sentinel в getStatChange, событие как маркер отключения, общий hook завершения способностей — не приняты как архитектура постоянного UI. Они обслуживают сбор свидетельств; перед производственной реализацией нужно проверить возможность убрать их и локализовать код прогноза. Нельзя считать отсутствие побочных эффектов доказанным только потому, что вызваны штатные Op_ChangeStat/Op_IntStatMod: board.fake не копирует весь мир. Доказательства корректности чисел, отсутствия изменений живого состояния и сохранности подтверждения/отмены остаются самостоятельными.

Повторная адресная проверка внешних источников не выявила готовый подтверждённый SDK текущего UI: [Mod Content](https://store.steampowered.com/app/306850/The_Banner_Saga__Mod_Content/) описывает JSON/PNG/FLA/SWF ассеты, а [репозиторий Stoic](https://github.com/stoicstudio/tbs-factions-2013) прямо обозначен снимком Factions 2013. Это граница осмотренных материалов, не утверждение об отсутствии других источников. [Heroic Mod](https://github.com/Owfrin/tbs-heroic) заявляет нашу версию TBS1, но его README/наличие не доказывают пригодность архитектуры числового UI. [FFDec Features](https://github.com/jindrapetrik/jpexs-decompiler/wiki/Features#editing-actionscript) прямо предупреждает об экспериментальном AS-редактировании и нестабильном встроенном Flex-маршруте.

Следующий выбор сборочного механизма перед расширением: сравнить текущий донорский маршрут с отдельной компиляцией нашего AS3-кода и минимальным внедрением. Вопрос — можно ли снизить зависимость от экспериментального компилятора и пересадки сложного тела, сохранив точные типы/namespace и исходный клиент. Если это требует ещё более широкой пересборки/ненадёжных заглушек, такая альтернатива может оказаться хуже; заранее её не выбираем. Текущую короткую runtime-проверку test.4 это не отменяет и не превращает в принятие архитектуры. Рост знаний сохраняется в владельцах фактов и проверках; сокращение будущего времени работы и отсутствие новых ошибок не гарантированы.

### ReferenceError числовой ветки test.4: проверка имени класса, 20.10.2026

Первое исполнение прогноза получило ReferenceError #1065 после включения fake, до формирования строк результата; ветка восстановления записала restored=true и отключила пробу. Это не совпадение чисел и не полная приёмка безопасности. Свидетельство — TEST_BUILD_LOG.md. По исходной классовой таблице и импорту штатного BattleAbility найдено конкретное расхождение: наш IMPORTS ошибочно указывал engine.battle.ability.model.AbilityReason, а класс находится в engine.battle.ability.effect.def.AbilityReason. В доноре/установленной ветке остались неверные QName у findpropstrict и constructprop перед checkEffectConditionsAbility. Компилятор сформировал SWF несмотря на несуществующий импорт.

Исправляется исходный импорт; сборщик до компиляции сопоставляет весь список игровых классов с ABC проверенного оригинала. Единственное явное исключение списка — flash.utils.Dictionary, предоставляемый runtime, а не игровым ABC. Синтетические тесты отвергают неверный пакет и неизвестный внешний импорт, разрешают точный игровой класс и явно известный runtime-класс. Этот контроль не проверяет все методы/доступ/типы и не заменяет AIR. Ошибка возникла из-за непроверенного идентификатора в нашем коде; новое глобальное правило не требуется. Отдельный новый номер test.5 нужен из-за неизменяемости test.4. Поскольку найден локальный ошибочный импорт, узкий эксперимент с нативными ARMOR-операциями остаётся обоснованным; перед производственным UI прежняя оценка сборочной цепочки/изоляции остаётся открытой.

### Первое числовое совпадение и следующий представительский случай, 20.10.2026

На test.5 реальный «Таран» ранга 1 по свободному пути дал MATCH прогнозу всех восьми фигур; журнал/точные поля/хеши — TEST_BUILD_LOG.md. Это закрывает только базовый случай нижних ARMOR-операций и проверяемого восстановления; проекция изменившейся ауры, пересечения и низкая броня остаются открыты. Расширять этот вывод до полного симулятора или готовой производственной архитектуры нельзя.

Для короткого следующего испытания допустима союзная цель: в SPECIAL_BATTERING_RAM штатного BattleAbilityTargetRule запрещается цель, которую нельзя атаковать, только если она также не из команды кастера; затем проверяются mobile/осевая геометрия/наличие конца пути. Оба ARMOR-подэффекта имеют targetRule ANY. Поэтому связка Эгиль (pas_shieldwall) — соседний Рук (pas_light_step, без ответного pas_returnthefavor) даёт управляемый тест разрыва соседства, без ожидания удобного хода AI. ### Повторные fake-расчёты с аурой: синхронизация Stat, 20.10.2026

Вопрос: почему при неизменных исходных числах первый прогноз Руку ARMOR=8 совпал с настоящим результатом, а следующие дали 9? Свидетельство/граница — TEST_BUILD_LOG.md. Повторно исследованы исходные Entity/Stats/Stat/StatMod; p-code этих четырёх классов экспортирован из оригинального SWF и сохранён с локальным manifest, вне Git.

Entity.setFakeEntityStats(true) создаёт _fakeStats через clone только в первый раз, затем вызывает synchronizeFrom. У Stat.synchronizeFrom условие выбора обновления существующей записи действительно проверяет `destinationMods.length < index`: это подтверждено парой getproperty length / getlocal index / ifnlt в исходном p-code, а не только AS-декомпиляцией. Для обычных индексов 0..source.length-1 метод добавляет новые модификаторы к прежним и обрезает хвост до исходного количества; в конце отдельно присваивает source._value. Поэтому одинаковые base/value не доказывают одинаковый набор providers. Удаление ауры из fake Stats в нашей пробе меняет этот набор; при следующей синхронизации старые посторонние записи могут вытеснить восстановленную запись ауры. Это согласуется с первым правильным/последующими ошибочными прогнозами и корректным Эгилем; конкретный состав кэша test.5 не логировал. Также Stat.testEquals сравнивает type/value/base/original, но не модификаторы; прежний restored=true не закрывал эту область.

Пересмотр механизма перед продолжением: (1) патчить общий Stat.synchronizeFrom — затронет все штатные fake-потребители, шире задачи; (2) заменить Entity._fakeStats через private-доступ — новая хрупкая интеграция, не выбрана; (3) очистить только доступный fake Stats публичным synchronizeFrom(empty), затем synchronizeFrom(snapshot) — выбранный узкий исследовательский вариант. По p-code Stats.synchronizeFrom(empty) удаляет все Stat; при последующем заполнении пустого контейнера каждый Stat проходит clone/internalAddStat, а не дефектную ветку Stat.synchronizeFrom. Повторять эту процедуру также перед выходом, чтобы не оставлять штатным потребителям изменённый кэш. Живые Stats и формулы/округление/аура игры не заменяются. Отдельные proxy-entity/копия мира значительно сложнее и пока не нужны.

Test.6 проверяет соответствие диагностических getDebugStringMods у исходной копии, свежего fake-контейнера и восстановленного кэша; сравнение реальных модификаторов добавлено к прежним инвариантам. Это исследовательское сравнение родных описаний providers/amount/charges, не парсер игрового правила и не полная объектная транзакция. До очистки записывается cacheWasStale, после — cacheRestored; ошибка очистки ловится до обязательного board.fake=false. Инициализация/очистка выполняются только внутри уже разрешённой fake-ветки. Такой механизм ещё требует AIR-проверки повторных просмотров и настоящего результата; производственный READY этим не получен. Игровой материал/исходный p-code не публикуется; новое глобальное правило не требуется.

Реальные Stats, modifiers, positions, active effects, action/targetSet и live RNG проверяются после обязательного cleanup; строки публикуются только при полном ready/restored.

Граница первой пробы: штатно выбранная непустая линия NeedleI–III, текущий ход без ожидающего перемещения, нелетальный результат. Allied endpoint разрешён по baseline. Неизученные эффекты/таланты, KILL_STOP/IMMORTAL/TWICEBORN/крит/диверсия/поглощения/recourse/transfer/особый attack modifier дают unsupported до fake-входа; fake RNG не должен потребляться. Положительные заряды StatMod могут вызвать живого provider даже у клона, поэтому заряженные modifiers исключены через params и exact-build diagnostic-string guard. Это исследовательские ограничения, не принятый release support и не пользовательский fallback.

Разрешены только изученные Puncture/LightStep/ShieldWall/Stonewall/ReturnTheFavor/HeavyImpact; RTF у поражаемой цели отвергается, пока label не реализован. HeavyImpact допускается у другого бойца: WAIT_FOR_ACTION_COMPLETE использует casterRule SELF относительно caster пассивы; проверяется именно caster завершившейся атаки. Чужой Needle не запускает этот ответ владельца HeavyImpact. При совпадении с caster пробы — unsupported. Native условия реакции не вызываются ради запроса: mutating handler не является чистым API. Resistance labels берутся из EffectTag RESISTING_ARMOR/STRENGTH операции, не из присутствия Stonewall.

**Независимый consumer.** BattleAbility.handlePostComplete отправляет собственное ABILITY_AND_CHILDREN_COMPLETE после завершения effects/children, затем уведомляет manager, затем вызывает setFinalCompleted. Последний вызывает callback, способный сменить ход, раньше FINAL_COMPLETE. Поэтому observer подписан на событие точного выбранного действия; считывает настоящие ARM/STR и tags настоящих action.effects до callback, сравнивает target order/rank и пишет MATCH/MISMATCH. Это не запуск нашего расчёта повторно. Пара снимается после наблюдения, следующего запроса и dispose; максимум одна. Снимок может включать реальные реакции, поэтому их пути ограничены guards; каскадный прогноз этим не заявлен.
