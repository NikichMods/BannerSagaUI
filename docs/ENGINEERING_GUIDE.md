# Инженерный справочник Banner Saga

Рабочие знания, которые должны сокращать повторное исследование при создании модов. Ближайшая цель — BannerSagaUI для TBS1; полезные методы сохраняются с расчётом на трилогию, без обещания совместимости трёх клиентов. Это практический вход, не полный исходник движка и не отдельный обязательный дневник каждой операции.

Отдельный потребитель этих знаний — [BannerSagaFPSFix](https://github.com/NikichMods/BannerSagaFPSFix/tree/research/first-release), самостоятельный патчер статичных портретов. Здесь остаются исходные host-находки и test.7/test.8 в RESEARCH.md/TEST_BUILD_LOG.md; новые установка, откат, совместимость и версии FPS-продукта принадлежат тому проекту. При новых модах по-прежнему начинать с этого справочника, не копировать историю целиком.

## Что известно о клиенте и границы переноса

TBS1 исследована на Steam Windows, application 2.58.17 / build 3268685. Версии и SHA-256 трёх установок находятся в SEQUEL_COMPARISON.md, база первой пробы — `data/baseline.json`. Перед применением инструкции к другой установке сверять её владельцев/структуры; одинаковое имя класса ещё не доказывает одинаковую работу.

| Знание | Что проверено | Что нельзя из этого заключать |
|---|---|---|
| AIR/SWF, штатный загрузчик сжатого AMF3 | Путь загрузки и правка одной русской строки TBS1 | Любой `.json.z` — текстовый JSON или поддерживается нашим узким Reader |
| Flash display-list UI; в клиенте присутствует и Starling | Владельцы конкретных подсказок TBS1 | Весь UI управляется одним графическим слоем |
| Выбранные экспорты UI-классов трилогии совпадают/различаются | Ограниченная матрица в SEQUEL_COMPARISON.md | Полная бинарная, игровая или ресурсная совместимость частей |
| Узкий импорт p-code одного метода FFDec | Контроль содержимого, одно изменение и повторяемые байты TBS1 | Клиент прошёл верификатор AIR, запустился или новая функция принята |

Документация формата ABC: [Adobe AVM2, ABC 46.16](https://github.com/adobe/avmplus/blob/master/doc/abcFormat-46-16.txt). Это описание формата, не документация API Banner Saga; сам документ предупреждает о неполном охвате. Поведение игры устанавливаем по конкретному клиенту. Официальный Mod Content и исторические исходники Factions — указатели из RESEARCH.md; они не заменяют исходники/контракт современной TBS1.

## Частые рабочие маршруты

### Прочитать ресурс или изменить текст

Сначала установить реальный загрузчик и потребителя. В исследованной базе локализация — zlib + AMF3, несмотря на имя `strings.json.z`. `tools/amf3.py` поддерживает узкое наблюдённое подмножество; не обходить его отказ догадками о другом типе ресурса. Для существующей текстовой пробы использовать `tools/build.py` и команды из README. Цена способности, полнота боевого прогноза и геометрия подсказки имеют других владельцев: изменение перевода их не исправляет.

### Исследовать или точечно изменить код SWF

Использовать проверенные FFDec/JRE из RESEARCH.md; конкретные локальные пути — в `local/RESUME.md`. Работать с копией/локальным выходом, не писать результат поверх установленного оригинала. Пример CLI, где `<ffdec>` означает настроенный локальный запуск FFDec:

```text
<ffdec> -selectclass <fully.qualified.Class> -export script <local-output> <original.swf>
<ffdec> -format script:pcode -selectclass <fully.qualified.Class> -export script <local-output> <original.swf>
python tools/research/abc_index.py <original.swf> <fully.qualified.Class>
<ffdec> -replace <original.swf> <local-result.swf> <fully.qualified.Class> <complete-method.pcode> <body-index>
python tools/research/compare_swf.py <original.swf> <local-result.swf>
```

Сначала выполнить контроль с неизменённым методом. Импорт p-code должен содержать исходное описание метода: имя, параметры, возвращаемый тип, флаги, тело и таблицу исключений, когда она присутствует. **Не ограничиваться списком инструкций:** наша первая сокращённая проба сохранила тело, но потеряла параметры. Сравнение должно учитывать сигнатуры, константы, traits, исключения, другие тела, ресурсы и заголовок кадра. Индекс тела заново определять из точного оригинала, не переносить число из записей другой сборки.

Оба оригинальных инструмента в `tools/research/` только читают файлы; не патчат SWF и не запускают игру. Индексатор ограничен FWS/CWS и ABC 46.16, незнакомые структуры отклоняет. Сравнение показывает структурные различия по индексам; при перестановке таблиц это **не семантический diff** и не верификатор AVM2. В подробном отчёте выводятся только первые 12 изменений каждого списка, отдельные счётчики показывают полный размер. Для строгого контроля узкой правки неожиданные различия требуют разбора, а не предположения об их безвредности.

Проверенная ловушка: AS-экспорт BattleBoardController содержит метку/`§§goto`, поэтому неизменённый полный класс не компилируется. Не переписывать соседнюю логику движения ради такой ошибки; p-code отдельного метода обходит этот участок. Подробности контрольной и NOP-проб, хеши и границы — раздел подготовки эксперимента в RESEARCH.md. Эти файлы не предназначены для установки.

Другая проверенная ловушка FFDec 26.4.0: компиляция донорского AS с обработчиком try/catch внутри внешнего finally дала несовместимые высоты стека; test.3 получил VerifyError #1030 уже при входе в тренировочный бой. Удаления только вложенного finally недостаточно. В нашей пробе исправление — общий участок очистки после catch-all без ранних выходов, с отложенным форматированием ошибки после возврата из fake-режима. `check_pcode_stack.py` обнаруживает этот класс дефекта до импорта и проверяет итоговый экспорт; пять синтетических тестов не содержат игрового p-code. Это ограниченная проверка высот/переходов, не верификатор типов/доступа AVM2 и не замена первому запуску. Не отключать восстановление состояния ради обхода компилятора. Свидетельства/границы — RESEARCH.md и TEST_BUILD_LOG.md.

[Документация FFDec, Editing ActionScript](https://github.com/jindrapetrik/jpexs-decompiler/wiki/Features#editing-actionscript) прямо называет прямое AS-редактирование experimental, а встроенный маршрут через Flex SDK — unstable (перепроверено 20.10.2026). Поэтому переход на пункт меню Flex сам по себе не решает проблему доверия к сборке. При росте собственного кода сравнить отдельно компиляцию собственного модуля подходящим AS3-компилятором и минимальное внедрение с текущим донорским маршрутом; проверять конкретный результат в целевом AIR. Такой альтернативный маршрут у нас ещё не проверен. Не обещать полную пересборку клиента: официальный Mod Content описывает исходные ассеты, а опубликованный Factions — исторический клиент другой игры/версии.

В test.4 компилятор также пропустил несуществующий импорт AbilityReason: SWF собрался и вошёл в бой, но создание объекта в прогнозе дало ReferenceError #1065. Сверять игровые импорты с классами точного исходного ABC до компиляции; build_ram_probe.py теперь это делает. Проверка стека не доказывает разрешимость имён. Причина и тест — RESEARCH.md / TEST_BUILD_LOG.md.

TBS1 2.58.17: Entity переиспользует fake Stats через synchronizeFrom; исходный p-code Stat показывает проблемную синхронизацию списка модификаторов. Равные числовые значения и Stat.testEquals не доказывают равенство providers/charges. Test.5 дал первый правильный и последующие ошибочные прогнозы разрыва ауры. Узкий исследовательский обход в test.6 — заполнение очищенного fake-контейнера штатным clone-путём и восстановление кэша после просмотра; общий метод игры не патчится. Механизм и альтернативы — RESEARCH.md; runtime/приёмку проверять по TEST_BUILD_LOG.md.

### Работать с боевым предпросмотром

Найти владельцев результата, вывода и применения отдельно. Сейчас прослежены BattleAbility/getStatChange, Op_BatteringRam, AbilityDestinationOverlay, BattleBoardController и BattleHudPage; подробности — COMBAT_EXAMPLES.md и RESEARCH.md.

fake копирует характеристики, но не весь мир; «Таран» вообще исключён из штатного прогнозного исполнения. Успешный вызов/ноль не означает полный итог. Для конечной брони проверять не только урон/base, но и value с модификаторами: «Стена щитов» пересчитывается на MOVE_FINISHING и может менять числа соседей без прямого удара. Не двигать настоящую фигуру ради прогноза: Op_Aura меняет постоянные эффекты, а WalkTilesBehavior вызывает столкновения/триггеры; fake пропускает ответы Op_WaitForActionComplete. Проверяемый нижний seam Effect.execute/apply вместо полного BattleAbility.execute и границы его применения описаны в RESEARCH.md; безопасность/полнота ещё не доказаны. Порядок ввода тоже существенен: HOVER_TILE отправляется до назначения hoverEntity, а клавиатурный/геймпадный перебор связан с выбором цели. Поэтому новый preview нельзя строить простым вызовом обработчика клика на hover. Мышиный hover доказан ограниченной пробой test.2; ограниченный числовой набор прошёл native-сверку test.6/test.9 (точные границы — TEST_BUILD_LOG.md). Это не готовый постоянный UI. COMBAT_PREVIEW_TECHNICAL.md содержит найденные нативные экранные якоря/владельцев, рекомендуемый прямой контракт результата и открытые вопросы сборки, актуальности и стоимости.

### Добавить собственные классы и проверить их без игры

Для проверенной TBS1/FFDec26.4.0 появился отдельный исследовательский маршрут: `tools/research/compile_preview.py` компилирует только оригинальные ActionScript-классы в новый ABC с таблицей типов исходного host; `build_field_preview.py` добавляет его отдельным тегом и импортирует только два ScenePage hook-тела. Это не полная AS-замена чужого класса. Сверять старые native pool-записи, сигнатуры/traits/все прочие тела и неизменность своего ABC после импорта. FFDec может пропустить неразрешённый import: успешная компиляция не является проверкой зависимостей. Явная class-проверка также не заменяет runtime binding/AVM2 verifier.

Автономный AIR harness с собственным appID позволяет проверять собственные Frame/Session/Layer без игровой загрузки, RNG и ручного боя. В испытанном AIR29 captive контейнере нужен extendedDesktop; desktop не доходил до конструктора. Свежий results.json + exit code обязательны. Он не проверяет native provider/жизненный цикл ScenePage и не эмулирует бой. Входы, приватный JPype bridge, команды и ограничения — [PREVIEW_BUILD.md](../tools/research/PREVIEW_BUILD.md). Runtime/tool binaries и игровые exports в Git не входят. Совместимость с TBS2/TBS3 не проверена.

### Подтвердить результат в игре

Для нового исследовательского кода проверен статический путь «AS-донор → символический p-code → отдельное тело»: tools/research/build_ram_probe.py. Полная AS-замена класса FFDec может перенумеровать множество чужих методов даже при прежнем числе тел; такой donor-SWF не устанавливать. В test.3 донор используется только для компиляции оригинального диагностического кода, затем переносятся activation-slots/exception-indices и проверяется нормальная ветка независимо от смещения меток. Все остальные тела/сигнатуры/старые записи pools сверяются. После исправлений исходников/компиляции ограниченная проба прошла AIR/runtime-сверки test.6/test.9; это не общий рецепт безопасного переноса любого метода или уже проверенный способ добавления собственных классов.

Проверка структуры/сборки, запуск AIR, наблюдение поведения и принятие UX — разные свидетельства. Использовать точный кандидат и тестовый профиль в принятой DEV-копии; сохранения не редактировать автоматически. Устанавливать при закрытой целевой игре после резервной копии и сверки хешей, не завершать игру за пользователя. Отдельная настройка Steam/SWF, изолированное хранилище и обновление хешей запускателя — DEVELOPMENT_ENVIRONMENT.md; порядок кандидатов и фактические результаты — CANDIDATES.md/TEST_BUILD_LOG.md. Сырые логи и скриншоты сохраняются локально; в Git попадают необходимые выводы и идентичность свидетельств.

**Открытая игра не мешает сборке из отдельного исходного дерева.** Для SWF-проб подготовить локальный baseline-root с проверенным оригиналом по относительному пути `win32/app.game-saga1.air.swf`. Установленную модифицированную копию не использовать как исходник следующей сборки и не откатывать ради компиляции. Закрытие требуется для замены установленного файла/отката; после замены клиент нужно запустить заново, горячая перезагрузка не доказана.

В исследованной TBS1 штатные журналы находятся в AIR application storage, `Local Store/gamelog/A-0.log.txt`, рядом встречаются предыдущие A-1/A-2. Для текущей работы читать хранилище **TheBannerSagaDev**, не старый журнал TheBannerSaga; машинный путь — local/RESUME.md. Читать и сохранять снимок можно при открытой игре; перед следующим запуском сохранить нужный сеанс, не полагаясь на дальнейшую сохранность текущего A-0. Зафиксировать время/размер/хеш снимка, процесс/старт, установленный hash, профиль, загрузку нужного экрана и ошибки. Активный лог может быть неполным. Сравнить типы ошибок с предыдущим сеансом, не объявлять любую старую ERROR регрессией. Штатный INFO-лог не фиксирует каждое наведение и не заменяет визуальное свидетельство; трассировку добавлять только для конкретного незакрытого вопроса. Для TBS2/TBS3 путь/состав журналов этим наблюдением не подтверждены.

## Что сохранять по мере работы

Сохранять результат, если он меняет следующий выбор или избавляет от повторного поиска: найденный владелец, рабочая команда, важная особенность формата, воспроизводимый отказ, причина отказа от подхода, граница совместимости. Достаточна короткая запись **задача → проверенная база/метод → результат → ограничение/следующее действие**, с путём/хешем свидетельства при необходимости. Не писать повторный рассказ о чате, ежедневный отчёт или каждую неудачную команду.

Повторяющийся рабочий приём поднимать в этот справочник; единичный эксперимент оставлять в RESEARCH.md; продуктовые решения — в PROJECT.md и владельце требований; точный runtime-тест — в TEST_BUILD_LOG.md. Оригинальный исследовательский код публиковать, когда он пригодится повторно и не содержит игровых материалов/частных путей. Не превращать временный скрипт в универсальный инструментарий заранее. Неудачный подход хранить вместе с условием пересмотра: другая версия инструмента, новая база или более узкий механизм.

## Публичные и локальные материалы

Публично: наши объяснения, ссылки на первичные источники, версии/хеши, оригинальные инструменты, синтетические тестовые данные и принятые решения. Даже маленькая p-code-выгрузка метода остаётся игровым материалом, не становится нашим исходником из-за текстового формата. Машинные абсолютные пути — только в локальных указателях. Границы лицензии — LICENSING.md.

Приватный репозиторий сейчас не нужен. Он не отменяет проектный запрет на хранение игровых материалов в Git. Если появятся наши собственные конфиденциальные материалы, выбрать место по конкретной потребности, не создавать второй склад всей разработки. Сырой локальный материал не считать сохранённым на GitHub: для восстановления на другой машине нужны своя установка и инструменты.
